# แผนย้อนกลับเมื่อ deploy พัง (T31)

ใช้เมื่อหลัง merge เข้า `main` (= deploy Production ทันที) หรือหลัง apply SQL แล้วเว็บพัง
ข้อมูลผิด หรือเกิดช่องโหว่ เป้าหมายคือหยุดความเสียหายให้เร็วที่สุด **โดยไม่ทำข้อมูลหาย**

## หลักการ

1. **ย้อนโค้ดก่อนเสมอ** — เร็ว (ไม่ถึงนาที) และไม่แตะข้อมูล
2. **ย้อน SQL เป็นทางสุดท้าย** — ส่วนใหญ่ไม่จำเป็น เพราะแอปทำงานได้ทั้งก่อนและหลัง apply
   (มีทางสำรองเมื่อไม่พบ view/ฟังก์ชันใหม่) การแก้ไปข้างหน้าด้วยไฟล์ใหม่มักปลอดภัยกว่า
3. **Staging ก่อน** แม้เป็นการย้อน ยกเว้น Production ล่มอยู่ ให้เจ้าของโปรเจกต์อนุมัติแล้วทำ Production ได้เลย
4. จดทุกอย่างลง "บันทึกเหตุการณ์" ท้ายไฟล์นี้: เวลา อาการ สิ่งที่ทำ ผลลัพธ์

## ตัดสินใจเร็ว

| อาการ | ทำอะไร |
| --- | --- |
| หน้าเว็บ error / ขาว / 500 หลัง merge | ก. ย้อนโค้ดบน Vercel |
| ล็อกอินไม่ได้ทั้งระบบ | ก. ย้อนโค้ด แล้วตรวจ Supabase Auth (ไม่ใช่เรื่อง SQL ของเรา) |
| ฟีเจอร์เดียวพังหลัง apply SQL ไฟล์หนึ่ง | ข. ดูตารางย้อน SQL ของไฟล์นั้น |
| ข้อมูลถูกลบหรือแก้ผิดจำนวนมาก | ค. กู้จาก backup (หยุดเขียนข้อมูลก่อน) |
| ข้อมูลส่วนตัวรั่ว | ก. ทันที + แจ้งเจ้าของ/DPO ตามขั้นตอน PDPA |

## ก. ย้อนโค้ดบน Vercel

1. Vercel → โปรเจกต์ ballsai → **Deployments**
2. หา deployment Production ก่อนหน้าที่ยังดีอยู่ (ดูเลข commit และเวลา) — ต้องไม่เก่ากว่า
   "เวอร์ชันต่ำสุด" ในตารางถัดไป
3. เมนู `…` ของ deployment นั้น → **Promote to Production** (หรือ **Instant Rollback**) → ยืนยัน
4. เปิดเว็บจริงตรวจหน้าที่พัง จดเวลาที่ใช้
5. แก้ถาวร: ใน GitHub เปิด PR ที่ทำให้พัง → ปุ่ม **Revert** → merge PR ที่ revert
   (merge ต้องได้คำสั่งชัดจากเจ้าของเหมือนทุก PR) ถ้า Vercel แจ้งว่าพักการ deploy อัตโนมัติไว้หลัง
   rollback ให้ทำตามปุ่มที่ Vercel แสดงเพื่อเปิดคืนหลัง merge

## ค. กู้ข้อมูลจาก backup

ใช้เมื่อข้อมูลเสียหาย ไม่ใช่เมื่อโค้ดหรือ schema พัง

1. หยุดการเขียนข้อมูล: ย้อนโค้ดไปเวอร์ชันที่ดี (ข้อ ก.) หรือประกาศปิดปรับปรุง
2. Supabase → Database → Backups → เลือกจุดเวลาก่อนเกิดเหตุ
3. **กู้ลงโปรเจกต์ทดสอบก่อน** ตรวจว่าข้อมูลถูก แล้วค่อยตัดสินใจกู้ Production
4. ยังไม่เคยซ้อมจริง — เป็นงาน T29 (ต้องรู้ว่ากู้ได้จริงและใช้เวลากี่นาที)
