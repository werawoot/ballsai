UX: ทั้ง 5 flow — 6 ต.ค. 2026 — mockup (HTML → PNG) ใช้ token และฟอนต์ของแอป ภาพทั้งหมดเป็น **local mock** ไม่มีรูปเด็ก ไม่มีสถิติ ("—" คือโครง ไม่ใช่ค่า) ยังไม่แก้โค้ดแอป

หนึ่งจอ = หนึ่งคำถาม · ปุ่มหลักปุ่มเดียวอยู่ล่างจอ · แตะตัวเลือก = ไปต่อเลย · มีค่าเริ่มต้นให้ทุกอย่างที่เดาได้ · ไม่มีการ์ดซ้อนการ์ด ไม่มีป้ายสถานะที่ไม่จำเป็น · ไม่มีตัวนับวันต่อเนื่องหรือข้อความตำหนิ

## สิ่งที่ต้องให้ lead ตัดสินก่อนสร้างจริง (ไม่ใช่เรื่องดีไซน์)

1. **เก็บวันเกิดตั้งแต่ตอน onboarding (v2-1 จอ 2)**: ระบบเก็บวันเกิดอยู่แล้ว (มีใน `/profile/edit` และ trigger ของ SQL guardian-consent) แต่การถามตั้งแต่ก่อนเห็นการ์ดเป็นการเปลี่ยนจังหวะการเก็บข้อมูลเด็ก ต้องให้เจ้าของและฝ่ายกฎหมายเห็นชอบ ถ้าไม่ผ่าน ให้ถามเฉพาะชื่อและตำแหน่งก่อน (ลด 1 ช่อง)
2. **ลิงก์ผู้ปกครองแบบมีโทเค็น (v2-2 จอ B)**: ปัจจุบันผู้ปกครองต้องพิมพ์อีเมลลูก (`request_guardian_link`) การไม่ต้องพิมพ์ต้องมีโทเค็นหมดอายุ ใช้ครั้งเดียว และผูกกับบัญชีเด็ก ต้องออกแบบพร้อมตรวจสิทธิ์/RLS ไม่ใช่งาน CSS ข้อความยินยอมยังเป็น `[รอนักแปลกฎหมาย]`
3. **การแจ้งเตือนในแอป (v2-2 จอ C)**: `AGENTS.md` ระบุว่าการแจ้งเตือนในแอปเป็นงานก่อนขยายเกิน 5 คน จอ C พึ่งสิ่งนี้ ถ้ายังไม่มี ให้ใช้ป้ายเตือนบน `/profile` แทน
4. **เชิญหลายอีเมล (v2-4)**: ต้องแก้ API ให้ idempotent, มี rate limit, และ**ไม่แยกผลระหว่างอีเมลที่มีและไม่มีบัญชี** ปัจจุบัน `app/api/teams/[teamId]/members/route.ts` ตอบ "ยังไม่มีบัญชีนี้ในระบบ" ซึ่งเป็นช่องให้เดาอีเมลในระบบที่มีข้อมูลเยาวชน (ระบุไว้ในรายงานรอบ 1 แล้ว)
5. **ผู้ทำประตูที่ไม่ระบุตัวของทีมตรงข้าม (v2-3)**: ถ้าไม่ลงผู้ทำประตู ระบบ Rating ใช้ได้ไหม ต้องเช็กกับ `match_results` ว่าสกอร์ทีมกับผลรายคนผูกกันอย่างไร ผมยังไม่ได้อ่านส่วนนั้น
6. คำถาม "nationwide use" 5 ข้อ ยังไม่ได้ตอบสำหรับข้อ 2 กับ 4 ข้างบน จึงไม่ถือว่าพร้อมสร้าง

## ที่ยังไม่ได้ทำ

ขั้น "เลือกนัดจากตาราง" ของผู้จัด · สถานะ 0 / 1 / 1,000 รายการ, offline, error · ทดสอบข้อความไทยยาวมาก · ตรวจที่ 320 px · ทดสอบกับคนจริง · วัดการแตะจริงด้วย event ในแอป (ตอนนี้แอปยังไม่มี event เหล่านี้)
