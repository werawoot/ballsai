# UX audit รอบที่ 1 — 5 flow แบบผู้ใช้ครั้งแรก

UX: 5 flow ตาม "Where to start" — 6 ต.ค. 2026 — ดูบน **local mock** (build บนเครื่องชี้ไปที่ Supabase จำลอง ไม่ใช่ Preview/Staging/Production)

## ขอบเขตและความจริงใจเรื่องหลักฐาน

- ดูจาก build ของ `claude/beautiful-rubin-xyygat` (`6b676a9`) ด้วย Chromium มือถือ 390 × 844 และจอคอม 1280 × 800 ข้อมูลทุกอย่างในภาพเป็นข้อมูลสมมติจาก mock ที่ผมเขียนเอง (ชื่อ "น้องตัวอย่าง" ฯลฯ) ไม่มีรูปเด็ก ไม่มีสถิติจริง
- mock ไม่ใช่ Supabase จริง: **ไม่ได้พิสูจน์** RLS, สิทธิ์, การอัปโหลดรูป/สลิป, การล็อกอิน Google/OTP และความเร็วบนเครือข่ายจริง ภาพสลิปที่แสดงเป็นรูปแตก เป็นผลจาก mock ไม่ใช่บั๊กของแอป
- **ยังไม่ได้ดู** (mock ยังไม่ครอบคลุม): `/ranking`, `/dashboard/tournaments/[id]/fixtures`, หน้ารายละเอียดโปรแกรม `/training/[programId]`, การอัปโหลดสลิปของโค้ช, ขั้น 2–3 ของ `/welcome` (อ่านจากโค้ด `OnboardingFlow.tsx`) และการกดปุ่มจริง (บันทึก/ส่งคำเชิญ) ถ้าต้องการ ผมขยาย mock ได้ในรอบถัดไป
- ยังไม่ได้ทดสอบบนมือถือจริง กลางแดด หรือ 4G ช้า "ตัวเลขจำนวนแตะ" ด้านล่างนับจากหน้าจอและโค้ด ไม่ได้จับเวลากับคนจริง
- ไม่ได้แก้โค้ดของแอป ที่เพิ่มมีเฉพาะ `docs/ux-audit/` (รายงาน ภาพ และ HTML ของ mockup)

## ปัญหา (เรียงจากกระทบคนมากที่สุด)

1. **[นักกีฬาอายุต่ำกว่า 20 · ผู้ปกครอง]** ขั้น "ผู้ปกครองรับรู้" คอขวดของเส้นทาง แต่อยู่ลำดับที่ 4 ใน checklist
   - ทำไมเป็นปัญหา: `lib/profile-readiness.ts` เรียงขั้นเป็น ข้อมูลพื้นฐาน → รูป → ตำแหน่ง/ทีม → **ผู้ปกครอง** → ไฮไลต์ → เปิดสาธารณะ ปุ่ม "ขั้นต่อไป" ของ `/profile` จึงพาไปทำรูปก่อน (ดู `audit-f1-profile-minor-m.png`) ทั้งที่ขั้นผู้ปกครองต้องรอผู้ใหญ่หลายวัน และเป็นเงื่อนไขของโปรไฟล์สาธารณะ → ได้ Ranking → บันทึกผลได้ (`docs/user-flows.md` §2.3) เด็กจึงทำรูป ตำแหน่ง ไฮไลต์เสร็จหมดแล้วไปติดที่ขั้นที่ต้องรอ นอกจากนี้ฝั่งเด็กที่เปิด `/guardian` เห็นปุ่ม "รับคำขอ / ปฏิเสธ" โดยไม่มีคำอธิบายว่ากดแล้วเกิดอะไร (`audit-f2-guardian-minor-m.png`) และฝั่งผู้ปกครองต้องรู้อีเมลบัญชีของลูกก่อน
   - ข้อเสนอ: เสนอขั้นผู้ปกครองให้เร็ว บอกว่า "ทำข้ออื่นระหว่างรอได้" มีสถานะ "รอผู้ปกครอง" ที่ไม่ขวางขั้นอื่น และบนหน้ารับคำขอบอกผลของ "รับ" กับ "ปฏิเสธ" ให้ชัด (ข้อความยินยอมจริงเว้นไว้ให้นักแปลกฎหมาย)
   - วัดผลด้วย: สัดส่วนนักกีฬาอายุต่ำกว่า 20 ที่ส่งลิงก์เชิญผู้ปกครองภายใน 24 ชม. หลังสร้างโปรไฟล์ · เวลากลางจากส่งลิงก์ → `guardian_consent_at` (มี `guardian_links.requested_at` และ `guardian_consent_at` อยู่แล้ว)
   - mockup: `img/m1-guardian-m.png`, `img/m1-guardian-d.png`

2. **[ผู้จัด]** หน้าบันทึกผลแข่งหน้าสนามยากเกินไป ทั้งที่เป็นหน้าสำคัญที่สุดของระบบ
   - ทำไมเป็นปัญหา: ฟอร์มเป็นชุด dropdown (รายการ, "Team A", "Team B", "ทีม", "นักกีฬา") ป้ายอังกฤษปนไทย (`MATCH RESULT`, `PLAYER PERFORMANCE`, `Player #1`, `Preview`, `Confirm Result`) รายการแข่งถูกเลือกแล้วด้านบนแต่ซ้ำเป็น dropdown อีกอัน ปุ่ม Confirm เทาโดยไม่บอกเหตุผล หัวข้อใช้ตัวอักษรเส้นขอบ (`MATCH RESULT`) ผิดกฎ design system ข้อ 3 และบนจอคอมช่องกรอกกว้างเต็ม 1,200 px (`audit-f4-results-m.png`, `audit-f4-results-d.png`) ผลหนึ่งนัดใช้การเลือก dropdown หลายครั้งบนมือถือกลางแดด และเป็นหน้าที่ผลแข่งทุกนัดต้องผ่านเพื่อให้ Rating ขยับ
   - ข้อเสนอ: แบ่งเป็น 3 ขั้น (สกอร์ → ผลงานรายคน → ตัวอย่าง/ยืนยัน) สกอร์เป็นปุ่ม − / + ใหญ่ ผลงานรายคนแตะที่ชื่อ (ประตูเพิ่มทีละ 1, MVP) ปุ่มหลักปุ่มเดียวติดล่างจอ บอกเหตุผลเมื่อกดไม่ได้ ไทยล้วน
   - วัดผลด้วย: จำนวนผลที่ยืนยันต่อผู้จัดต่อวันแข่ง · เวลาจากเปิดหน้าถึงยืนยัน (ต้องเพิ่ม event เวลาเริ่ม ตอนนี้แอปยังไม่มี) · สัดส่วน preview ที่จบด้วย confirm
   - mockup: `img/m2-results-m.png`, `img/m2-results-d.png`

3. **[โค้ช]** เชิญนักกีฬาได้ทีละอีเมล และหน้าไม่บอกว่าขั้นถัดไปคืออะไร
   - ทำไมเป็นปัญหา: ทีมหนึ่งมีหลายคน แต่ฟอร์มรับอีเมลเดียวต่อครั้ง (`/team-members`, `audit-f3-team-m.png`) ฟอร์มเชิญและปุ่ม "ส่งสมัครรายการ" อยู่ท้ายหน้า ใต้รายชื่อยาวที่แสดงสมาชิกคนเดียวซ้ำทั้งในรายการและในการ์ด หัวหน้าเป็น `TEAM ROSTER` สถานะ "กำลังจัด roster" ปุ่มส่งสมัครเล็กและไม่ใช่ปุ่มหลัก ตามกฎข้อ 4 ของ AGENTS.md "งานมือที่โตตามจำนวนผู้ใช้" ต้องหายไป การเชิญทีละคนคือหนึ่งในนั้น
   - ข้อเสนอ: ตัวบอกขั้น (สร้างทีม → เชิญ → ส่งสมัคร) ช่องวางอีเมลหลายอันพร้อมผลต่อแถว สรุปจำนวน ตอบรับ/รอ/ปฏิเสธ และปุ่มส่งสมัครเป็นปุ่มหลักติดล่างจอพร้อมเหตุผลเมื่อกดไม่ได้
   - วัดผลด้วย: จำนวนคำเชิญต่อทีม · เวลาจากสร้างทีมถึง `submit` · สัดส่วนทีมที่สร้างแล้วส่งสมัครสำเร็จ
   - mockup: `img/m3-coach-m.png`, `img/m3-coach-d.png`
   - **ต้องให้ lead ตรวจก่อนสร้างจริง** (ดูหัวข้อ "ความเสี่ยงที่พบระหว่างทาง")

4. **[นักกีฬาใหม่]** จาก `/welcome` ถึงการ์ดใบแรก ใช้ขั้นตอนมาก และการ์ดแรกยังไม่มีชื่อ
   - ทำไมเป็นปัญหา: ถึง `/card` ต้องแตะ ติ๊กยินยอม + Google (2) แล้ว `/welcome` เลือกบทบาท → ต่อไป → ต่อไป → เริ่ม (4) รวมอย่างน้อย 6 แตะ จากนั้นการ์ดแสดง `YOUR NAME` และ STARTER (ซื่อสัตย์ตามกฎข้อ 8 ดี) ต้องเปิดโปรไฟล์เพื่อกรอกชื่อ วันเกิด ตำแหน่ง (`audit-f1-card-new-m.png`, `audit-f1-profile-edit-m.png`) ทักทายด้วยส่วนหน้าอีเมล ("สวัสดี nong.new") ปุ่ม "ต่อไป" ที่ยังกดไม่ได้เป็นสีแดงเข้มจาง ไม่บอกเหตุผล (`audit-f1-welcome-m.png`) และมีป้ายอังกฤษ "Sponsor / Brand"
   - ข้อเสนอ: ถามชื่อที่ใช้บนการ์ดในขั้นสุดท้ายของ `/welcome` ให้การ์ดใบแรกมีชื่อทันที ปรับปุ่มที่ปิดอยู่ให้ชัดและบอกว่าต้องเลือกอะไร
   - วัดผลด้วย: สัดส่วนผู้ที่ล็อกอินแล้วเปิด `/card` ที่มีชื่อภายใน 10 นาที · แตะ "แชร์การ์ด" ต่อนักกีฬาใหม่
   - ยังไม่ทำ mockup (ตามที่ขอให้ทำ 3 ข้อแรก)

5. **[ผู้จัด]** ตรวจสลิปแล้วมีปุ่มยืนยันสองชั้นที่ไม่บอกความต่างกัน
   - ทำไมเป็นปัญหา: บนการ์ดทีมที่รอยืนยันมีปุ่มเขียว "ยืนยันการชำระเงิน" แล้วตามด้วยปุ่มแดง "ยืนยัน" และ "ปฏิเสธ" ของทีม (`audit-f4-dash-m.png`) ผู้ใช้ครั้งแรกไม่รู้ว่าต้องกดทั้งสองหรือไม่ ลำดับไหน และปุ่มแดงในที่นี้ถูกใช้เป็นปุ่มปกติ ไม่ใช่เตือน ต่อทีมต้องเลื่อนผ่านภาพสลิปขนาดใหญ่ก่อนถึงปุ่ม
   - ข้อเสนอ: หนึ่งการ์ดทีม หนึ่งลำดับ "ตรวจสลิป → ยืนยันชำระ → ยืนยันทีม" บอกสถานะแต่ละขั้น ย่อสลิปเป็นภาพย่อกดขยาย
   - วัดผลด้วย: เวลาเฉลี่ยจากทีมส่งสมัครถึงยืนยัน · จำนวนทีมที่ชำระแล้วแต่ยังไม่ยืนยันค้างเกิน 24 ชม.

6. **[ผู้จัด]** หัวข้อตัวอักษรเส้นขอบและข้อความอังกฤษปนไทยในหน้าชุดที่ 3
   - ทำไมเป็นปัญหา: `/dashboard`, `/dashboard/create`, `/dashboard/results` ยังไม่ผ่านการปรับตาม design system (ชุด 3 สถานะ ⬜) หัวข้อไทย "รายการแข่ง" ในหน้าสร้างรายการเป็นตัวอักษรเส้นขอบ อ่านยากกลางแดด และผิดกฎข้อ 3 (`audit-f4-create-m.png`) ปุ่ม 3 ปุ่มในแต่ละการ์ดรายการ (แก้ไข / ตารางแข่ง / ปิดรับสมัคร) เป็นปุ่มทึบเท่ากันหมด จึงไม่มีปุ่มหลัก
   - ข้อเสนอ: ทำตามชุด 3 ในตาราง "สถานะการนำไปใช้" ของ design system

7. **[นักกีฬาที่กลับมา]** `/profile` ยังเป็น checklist "ก่อนเปิดโปรไฟล์สาธารณะ" ทั้งที่เปิดไปแล้ว
   - ทำไมเป็นปัญหา: ใน mock ของนักกีฬาที่โปรไฟล์สาธารณะแล้ว หัวหน้าเขียน "4 จาก 6 ขั้น" และปุ่มแดงใหญ่พาไปทำรูป (`audit-f5-profile-m.png`) ไม่มีส่วน "วันนี้ทำอะไร" (ซ้อมวันนี้ นัดถัดไป อันดับล่าสุด) ให้เหตุผลกลับมาใช้ซ้ำ ผมยังยืนยันไม่ได้ว่าการ์ดฝึกซ้อมบน `/profile` แสดงอย่างไรเมื่อมีโปรแกรมจริง เพราะ mock ไม่มีข้อมูลโปรแกรม
   - ข้อเสนอ: ถ้าโปรไฟล์สาธารณะแล้ว ย่อ checklist เหลือสิ่งที่ขาด และเลื่อนส่วน "วันนี้" ขึ้นก่อน (รอตรวจกับข้อมูลโปรแกรมจริงก่อนออกแบบ)

8. **[ทุกคน · จอคอม]** เลย์เอาต์ยืดเต็มจอและแถบเมนูล่างแบบมือถือบนจอ 1280
   - ทำไมเป็นปัญหา: หน้าบันทึกผลบนจอคอมกว้างเต็ม 1,200 px (`audit-f4-results-d.png`) และแถบเมนูแบบแอปมือถือยังอยู่ด้านล่างจอคอม ผู้จัดหลายคนทำงานบนโน้ตบุ๊กที่โต๊ะลงทะเบียน (ข้อสันนิษฐาน ยังไม่มีข้อมูลยืนยัน)

หมายเหตุเรื่องภาพถ่ายหน้าจอ: แถบเมนูล่างที่ปรากฏกลางภาพยาวในไฟล์ `audit-*` เกิดจากการถ่ายภาพเต็มหน้า (`fullPage`) ไม่ใช่ตำแหน่งจริง

## ความเสี่ยงที่พบระหว่างทาง (ส่งให้ lead ตัดสิน ไม่ใช่เรื่องดีไซน์)

- `app/api/teams/[teamId]/members/route.ts` ตอบ `404 "ยังไม่มีบัญชีนี้ในระบบ"` เมื่ออีเมลไม่มีบัญชี ทำให้ใครก็ตามที่สร้างทีมได้ใช้เดาได้ว่าอีเมลไหนมีบัญชีใน BallDoenSai ในระบบที่มีข้อมูลเยาวชน นี่คือช่องให้ตรวจสอบการมีอยู่ของบัญชี (account enumeration) การเชิญหลายอีเมลพร้อมกัน (mockup 3) จะทำให้เดาได้เร็วขึ้น mockup จึงออกแบบให้ทุกแถวตอบ "ส่งแล้ว" เหมือนกัน และทำได้ก็ต่อเมื่อ API ไม่แยกผลกรณีไม่มีบัญชี พร้อม rate limit ต่อโค้ช
- mockup 3 ต้องตอบคำถาม 5 ข้อของ "nationwide use" ก่อนสร้างจริง: ส่งหลายอีเมลซ้ำต้องได้ผลเหมือนส่งครั้งเดียว (idempotent), มี rate limit, และไม่เพิ่มงานมือต่อทีม คำถามเหล่านี้ยังไม่ได้รับคำตอบ ผมจึงไม่ถือว่า mockup นี้พร้อมสร้าง

## ข้อสังเกตสำหรับ mockup ทั้ง 3

- ชื่อและตัวเลขในภาพเป็นตัวอย่างระบุ "(ตัวอย่าง)" ไม่ใช่สถิติ ไม่มีรูปเด็ก ไม่มีภาพจริง
- mockup 1 ไม่เขียนข้อความทางกฎหมาย: ช่องข้อความยินยอมถูกเว้นไว้เป็น `[รอข้อความจากนักแปลกฎหมาย]` ข้อความอธิบายตัวอย่างว่า "ถ้ากดรับ/ปฏิเสธ" เป็นข้อความการใช้งาน ขอให้ lead ตรวจว่าไม่เกินสิ่งที่ระบบทำจริงก่อนสร้าง
- ใช้เฉพาะ token ใน `app/ui.css` ปุ่มหลักหนึ่งปุ่มต่อจอ ปุ่มกดสูง ≥ 44 px ไม่มี horizontal scroll ที่ 390 px (ตรวจในเบราว์เซอร์แล้ว) แต่ยังไม่ได้ตรวจที่ 320 px
- ยังไม่ได้ทดสอบข้อความไทยยาวมาก สถานะ 0/1/1,000 รายการ สถานะ offline และ error ของ mockup เหล่านี้ ซึ่งต้องมีใน spec ก่อนส่งให้ lead สร้าง
