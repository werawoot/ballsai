# การเฝ้าระวังระบบ (T30)

เป้าหมาย: ถ้าเว็บหรือฐานข้อมูลล่ม หรือผู้ใช้เจอ error ต้องมีคนรู้ภายในไม่กี่นาที ไม่ใช่รอผู้ใช้บอก

## สิ่งที่แอปมีให้แล้ว

| อะไร | ที่ไหน | ใช้ทำอะไร |
| --- | --- | --- |
| `GET /api/health` | `app/api/health/route.ts` | ตอบ `200 {"status":"ok"}` เมื่อแอปและฐานข้อมูลตอบ; `503 {"status":"degraded"}` เมื่อฐานข้อมูลไม่ตอบหรือช้ากว่า 3 วินาที; บอกเวอร์ชัน (commit 7 ตัว) และเวลาที่ฐานข้อมูลใช้ ไม่มีข้อมูลผู้ใช้หรือข้อความ error ของฐานข้อมูล |
| log ฝั่งเซิร์ฟเวอร์ | `lib/monitoring.ts` | ทุก error เป็น JSON หนึ่งบรรทัด `{"app":"ballsai","level":"error","event":"…"}` ใน log ของ Vercel |
| error ฝั่ง browser | `app/error.tsx`, `app/global-error.tsx` → `POST /api/client-errors` | หน้าเว็บที่พังในเครื่องผู้ใช้ส่งรายงานมาเป็น event `client_error` ใน log เดียวกัน ตัดอีเมล ตัวเลขยาว และ query ของ URL ออกก่อนบันทึก จำกัด 20 ครั้ง/นาที/IP |
| smoke test | `npm run smoke:public` | ตรวจหน้าสาธารณะและ `/api/health` ของ deployment ใดก็ได้ (`BASE_URL=…`) |

## สิ่งที่เจ้าของต้องตั้ง (ครั้งเดียว)

1. **Uptime monitor** — บริการใดก็ได้ที่เรียก URL ตามรอบและแจ้งเตือนได้ (เช่น UptimeRobot, Better Stack,
   Checkly หรือ monitor ของ Vercel ถ้าแพ็กเกจมี)
   - URL: `https://<โดเมน Production>/api/health`
   - ทุก 1–5 นาที, ถือว่าล่มเมื่อสถานะไม่ใช่ 200 หรือไม่มีคำว่า `"status":"ok"`
   - แจ้งเตือนไปอย่างน้อย 2 ช่องทาง (อีเมล + LINE/โทรศัพท์) และอย่างน้อย 2 คน
   - ตั้งอีกตัวสำหรับ Staging ได้ แต่แจ้งเตือนแยก
2. **แจ้งเตือนจาก log** — ใน Vercel (Observability / Log Drains ตามแพ็กเกจ) หรือบริการ log ที่ต่อด้วย
   log drain: ตั้งแจ้งเตือนเมื่อ `level":"error"` เกิน N ครั้งใน 5 นาที และแยกดู `event":"client_error"`
3. **ทดสอบว่าแจ้งเตือนถึงจริง** (เงื่อนไขปิด T30): บน Staging ทำให้ health ตอบ 503 ชั่วคราว (เช่น ตั้ง
   monitor ชี้ไป URL ที่ไม่มีอยู่ หรือหยุดโปรเจกต์ Supabase ทดสอบ) แล้วดูว่าได้รับแจ้งเตือนภายในกี่นาที
   จดผลในตารางด้านล่าง
