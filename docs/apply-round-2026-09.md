# รอบ apply SQL: เปิดใช้งานเจ้าของสนาม โค้ช และผู้จัด (กันยายน 2026)

เอกสารนี้คือขั้นตอนทีละข้อสำหรับเจ้าของโปรเจกต์ ให้ฟีเจอร์ที่โค้ดเสร็จแล้ว (🟡) ใช้งานได้จริง
ทุกไฟล์ต้องผ่าน **Staging (`vorpnkedpscsqhnrssrl`) ก่อน** แล้วจึงขออนุมัติแยกสำหรับ
**Production (`hivedzrwrrcnjrlirhtv`)** ตามกฎใน [`AGENTS.md`](../AGENTS.md) ข้อ 2–3

กติกาทุกขั้น:

1. เปิด SQL Editor แล้ว **ตรวจ ref ใน URL** ให้ตรงกับฐานที่ตั้งใจ
2. รัน precheck ของขั้นนั้น เทียบกับ "ผลที่ควรได้" ในไฟล์ ถ้าไม่ตรง **หยุด** แล้วส่งผลมาให้ตรวจ
3. รันไฟล์ migration ทั้งไฟล์ในครั้งเดียว ทุกไฟล์มี `begin … commit` และตัวตรวจในไฟล์ ถ้าผิดจะ rollback เองทั้งหมด
4. รัน postcheck แล้วทดสอบบนเว็บตาม "ทดสอบบนเว็บ" ของขั้นนั้น
5. จดผล (สำเร็จ/ข้อความ error) ลงตารางท้ายเอกสารนี้

- **61 หลัง 60** — ฟังก์ชันของ SQL61 เรียก `record_match_result_once` ของ SQL60 และถอนสิทธิ์ anon ของตัวเองแล้ว จึงรันก่อนหรือหลัง SQL50 ก็ได้ (Staging ผ่าน SQL50 แล้ว จึงเป็นขั้น 20)

- **64 หลัง 63** — แก้สิทธิ์ของฟังก์ชันที่ SQL63 สร้าง: Supabase ให้ anon เรียกฟังก์ชันใหม่ได้ตรง ๆ จนกว่า SQL50 จะเปลี่ยนค่าเริ่มต้น การถอนจาก `public` อย่างเดียวจึงไม่พอบน Production (พบ 4 ต.ค. จาก fingerprint)
- **65 แทน 8** — ไฟล์ match-result-void เดิมตรวจสิทธิ์ด้วยการเปรียบเทียบที่ได้ NULL เมื่อไม่มี profile หรือรายการไม่มีผู้จัด และ `IF NULL` ไม่ปฏิเสธ (พบ 4 ต.ค. ก่อนรันบน Production) SQL65 เป็นฟังก์ชันเดิมที่แก้เงื่อนไขนั้นและถอนสิทธิ์ anon/service_role
- **ห้าม** `sql/supabase-rls-private-slips.sql`, `sql/sample-data.sql`, และ SQL20 ฉบับใดตรง ๆ (ดู `AGENTS.md` ข้อ 4 และ ADR-010)
- migration 49 (รายชื่อทีมตาม ADR-010) ยังไม่อยู่ในรอบนี้ — รอผล inventory-5
